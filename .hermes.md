# Home Manager Configuration

This repository contains the standalone Home Manager configuration for the workstation hardware profiles.

## Current state

Before proposing or making changes, read `CURRENT-STATE.md`. Keep it updated whenever architecture, profiles, shared defaults, workflows or important operational assumptions change.

## Model

- Intended public repository: `stdruwe/home-manager-workstations`
- Matching public NixOS repository: `stdruwe/nixos-workstations`
- Public release series starts at `v0.1.0`
- Standalone Home Manager flake: `flake.nix`
- Supported hardware profiles:
  - `thinkpad-x1-carbon-gen13`
  - `hp-z2-tower-g9`
  - `apple-macbook-air-8-1`
- No username or hostname is encoded in a profile name
- No generic username compatibility alias and no root `home.nix` compatibility entrypoint
- Local username/home are derived from `USER` and `HOME`
- Evaluation therefore requires explicit `--impure`
- `flake.lock.bootstrap` is the tracked clean-checkout/install baseline
- live `flake.lock` is ignored and machine-local
- Desktop-neutral user configuration lives in `modules/common.nix`
- Plasma-specific user configuration lives in `modules/desktops/plasma.nix` and is selected explicitly by ThinkPad/HP
- the MacBook profile is common-only in Home Manager; COSMIC is owned by the NixOS system configuration

The Home Manager repository can live at the current user's normal configuration path; do not hard-code a particular username into modules or documentation when `$HOME`/Home Manager data already provides the path.

Documentation should use technical profile names, hardware descriptions and generic placeholders rather than deployment-specific hostnames or personal usernames.

## Relationship to NixOS

The system NixOS configuration is separate at `/etc/nixos` and comes from `stdruwe/nixos-workstations`.

The NixOS repository keeps its canonical machine-local recovery state under `/etc/nixos/local/`:

- `/etc/nixos/local/profile.nix` — technical hardware selector
- `/etc/nixos/local/identity.json` — machine/user identity
- `/etc/nixos/local/deployment.json` — deployment-specific infrastructure or `{}`

Home Manager mirrors only the hardware profile distinction and obtains the current Unix user independently from the environment. When a user-level integration needs non-secret deployment data, it must normally read `/etc/nixos/local/deployment.json`. The historical `/etc/nixos/deployment.json` path may be retained only as migration/bootstrap fallback compatibility; do not use it as the documented installed-system path.

Do not move Home Manager configuration into `/etc/nixos` and do not convert the NixOS system configuration into a flake unless explicitly requested.

Before changing system packages, hardware, boot, networking, containers, firewalls or system services, inspect the NixOS repository and its `CURRENT-STATE.md`.

## Profile ownership

- `thinkpad-x1-carbon-gen13`: common + Plasma + Hermes
- `hp-z2-tower-g9`: common + Plasma, no Hermes
- `apple-macbook-air-8-1`: common only, no Plasma/Hermes; explicit Bitwarden SSH agent handling

Do not make `modules/common.nix` implicitly Plasma-specific just because two profiles use Plasma.

## Operational invariant discipline

The paired NixOS repository owns the canonical rationale for non-obvious hardware and cross-repository behavior in `docs/operational-invariants.md`. Read that document before changing Home Manager values that participate in service ordering, fixed delays, one-time markers, hardware workarounds or NixOS/Home Manager hand-offs.

Do not treat a hard-coded delay, marker or wrapper as a cleanup candidate merely because it appears arbitrary locally. The HP Z2 panel bootstrap is the clearest example: its 35-second delay intentionally follows the NixOS 30-second KScreen layout application and both values form one tested startup invariant.

For persistent changes to such behavior:

1. identify the original failure mode before changing the value;
2. update the adjacent Home Manager comment with the reason, not only the effect;
3. update `CURRENT-STATE.md` when the operational contract changes;
4. update the paired NixOS `docs/operational-invariants.md` when the invariant is cross-repository;
5. review and test both repositories together when one side depends on the other;
6. if the historical reason is unknown, preserve the behavior while investigating instead of inventing a rationale or optimizing it away.

## Hermes

Hermes belongs only to the ThinkPad profile.

The current upstream Home Manager module separates installation from service/configuration state:

```nix
programs.hermes-agent = {
  enable = true;
  desktop.enable = true;
};

services.hermes-agent = {
  enable = true;
  # settings, environment, MCP, gateway/daemons
};
```

Do not restore removed `services.hermes-agent.installPackage` or manually install the desktop package in parallel.

Preserve existing Hermes configuration unless a requested change targets it. Never place API keys or other secrets directly in Nix expressions. Hermes secrets belong under the current user's `~/.config/hermes/hermes.env`.

Deployment-specific non-secret endpoints also stay out of this repository. `modules/hermes.nix` normally reads optional `/etc/nixos/local/deployment.json` keys `hermes.habUrl` and `hermes.ollamaBaseUrl`. It accepts the old root-level file only as migration/bootstrap fallback. A missing file or missing keys must remain a valid clean-checkout/CI state; local HAB/Ollama integration is omitted in that case. The HAB wrapper may also obtain `HAB_URL` from `hermes.env` at runtime.

For Node-RED flow changes, never deploy a partial flow. Stage the complete flow JSON in `$XDG_RUNTIME_DIR/hermes-node-red/`, run `validate_flow_file`, and only then use `update_flow_file`. The staged flow ID must exactly match the requested target ID. If validation fails, stop instead of attempting a partial or fallback deployment.

## SSH

Shared GitHub SSH routing uses `ssh.github.com` on port 443 with user `git` for authenticated development access.

Installed-system repository reads use the public HTTPS origin configured by the NixOS installer. The `apple-macbook-air-8-1` profile additionally selects `~/.bitwarden-ssh-agent.sock` as its OpenSSH identity agent and exports the corresponding absolute `SSH_AUTH_SOCK`.

## Fresh-install integration

Fresh NixOS installations use the combined version-matched release package from the NixOS repository. The package carries the matching Home Manager release as a local bundle, and the selected activation package is built into the target store during installation.

The installer seeds ignored `flake.lock` from tracked `flake.lock.bootstrap` before preflight and target-store builds. After installation, the Home Manager checkout uses:

```text
https://github.com/stdruwe/home-manager-workstations.git
```

The first graphical login is ordered after the one-time Home Manager activation. Do not regress this workflow back to a manual post-login bootstrap.

## Update workflow

Topgrade is owned by the NixOS repository. Normal installed machines pull their configured NixOS and Home Manager upstreams but never commit or push automatic dependency updates back to this repository.

The live ignored `flake.lock` belongs to the current machine. If managed dependency updates are enabled, Topgrade creates a temporary candidate lock, validates only the current hardware profile against that exact candidate, and replaces the live local lock only after successful validation. Failure leaves the previous local lock intact.

The NixOS-side `/etc/nixos/local/deployment.json` setting `topgrade.updateManagedDependencies` defaults to `true`; `false` freezes machine-local dependency advancement while repository synchronization and normal Home Manager activation continue.

Do not introduce publisher profiles, cross-machine update transactions, automatic dependency commits, or automatic dependency pushes. `flake.lock.bootstrap` is a release/clean-checkout baseline, not a file that clients rewrite.

## CI contract

All three profiles must evaluate from a clean checkout after seeding the tracked bootstrap lock. The ThinkPad CI path additionally supplies a documentation-only `/etc/nixos/local/deployment.json` and verifies that Hermes actually consumes its `hermes.habUrl`. This positive integration test protects the cross-repository deployment path; do not replace it with only a missing-file fallback test.

## Working rules

Before changing Home Manager:

1. Read `CURRENT-STATE.md`.
2. Read the paired NixOS `docs/operational-invariants.md` before changing non-obvious timing/workaround behavior.
3. Read `flake.nix` and the relevant profile/module files.
4. Preserve the hardware-based three-profile structure.
5. Put desktop-neutral shared user configuration in common modules rather than duplicating it per profile.
6. Keep Plasma-specific behavior under `modules/desktops/plasma.nix` and select it explicitly from the two Plasma profiles.
7. Keep hardware-specific behavior under `hosts/`.
8. Do not encode a hostname or username into profile names.
9. Preserve existing Hermes Agent configuration unless the requested change targets it.
10. Never place API keys, passwords, tokens, private hostnames or deployment-specific endpoints directly in Nix expressions.
11. Prefer declarative Home Manager configuration over imperative per-user changes.
12. Use `--impure` when evaluating supported profiles.
13. Keep `flake.lock.bootstrap` tracked and the live `flake.lock` ignored/machine-local.
14. Do not make normal Topgrade operation require write access to the upstream repository.
15. Use `/etc/nixos/local/deployment.json` as the canonical NixOS deployment path.
16. Keep public documentation focused on the current repository state.

## Validation / activation

For a clean checkout with no live lock, first copy `flake.lock.bootstrap` to `flake.lock`. Installed machines already have the local lock.

ThinkPad:

```bash
home-manager build --impure --flake 'path:.#thinkpad-x1-carbon-gen13'
home-manager switch --impure --flake 'path:.#thinkpad-x1-carbon-gen13'
```

HP Z2:

```bash
home-manager build --impure --flake 'path:.#hp-z2-tower-g9'
home-manager switch --impure --flake 'path:.#hp-z2-tower-g9'
```

MacBook:

```bash
home-manager build --impure --flake 'path:.#apple-macbook-air-8-1'
home-manager switch --impure --flake 'path:.#apple-macbook-air-8-1'
```

Normal day-to-day updates are expected to flow through Topgrade as documented in `CURRENT-STATE.md` and the NixOS repository.
